## Context

How a release works today:
- **Embed**: `deploy.sh stage|prod` runs `npm install` and `npm run build:embed-<env>`, then `aws s3 sync --acl public-read` to `s3://static-pundit/releases[/stage]`, then invalidates CloudFront distribution `E3JMMV8C3EZFVD` (region `eu-south-1`). The feed loads `pundit.embed.js` from there.
- **Chrome extension**: `npm run build:chrome-ext-<env>` builds the embed first (`build:embed-<env>`), then the extension. The zip is uploaded to the Chrome Web Store by hand. Stage and prod are two separate store items; the stage manifest is renamed "Pundit Annotator (STAGE)" by `src/chrome-ext/manifest.stage.json`.
- **Versions**:
  - prod manifest = `package.json` `version` (`1.13.0`);
  - stage manifest = `scripts/.stage.version` (`1.13.0.N`), bumped inside `getStageVersion()` (`scripts/chrome-ext-build.js`) on every stage build;
  - git tags stopped at `v1.9.2`.
- **Environment config**: `src/environments/local.stage.ts`, `local.prod.ts` and `chrome-ext-urls.stage.js` are git-ignored, generated by `pundit-deployment/scripts/render-env.sh`, and can point at a local deployment (`*.thepund.test`). Right now the stage files do point at `*.thepund.test`, so releasing stage as-is would ship local URLs. `local.prod.ts` is absent.
- **Fragile build step**: `scripts/postbuild.js` catches and logs its own errors, so `npm run build:*` can exit 0 with a broken `dist/`.
- **Chrome Web Store API**: V2 has been current since October 2025 (`chromewebstore.googleapis.com/v2/publishers/{publisherId}/items/{itemId}:upload|publish|fetchStatus`). Upload fails when the manifest version is not bumped. `fetchStatus` returns `publishedItemRevisionStatus` / `submittedItemRevisionStatus`, each with `state` and `distributionChannels[].crxVersion`. Auth uses an OAuth refresh token (scope `https://www.googleapis.com/auth/chromewebstore`) or a service account.

Constraints:
- Node `^22.22.3` (`engine-strict`). Existing scripts are CommonJS and use `fs-extra` and `minimist`.
- Run only on a developer machine, never in CI.

## Goals / Non-Goals

**Goals:**
- One command per environment releases the embed and the extension with the same version.
- No version jumps or drift without an explicit, typed override.
- Nothing goes live without two human confirmations. Nothing goes live from a dirty tree, from the wrong branch (prod) or with local-domain config.
- A clear record in git (commit + tag) and on S3 (`version.json`) of what is live.
- Stage builds no longer touch `.stage.version`.

**Non-Goals:**
- CI/CD automation, or pushing to the remote.
- Rollback of a release (the store has no rollback API; S3 rollback = re-release an older commit with a forced higher version).
- Generating the environment config files (that stays with `render-env.sh`).
- Staged rollout / `deployPercentage` (only for items with more than 10k weekly users).
- Releasing the `pdf-standalone` builds (already dropped from `deploy.sh`).
- Releasing embed-only or extension-only.

## Decisions

### D1. Node script with small modules, not a bash script
`scripts/deploy.js` is the orchestrator. Pure or thin helpers live in `scripts/deploy/`:

| Module | Role |
|---|---|
| `config.js` | per-environment constants: S3 prefix, invalidation path, CloudFront ID, expected API host, CWS item env var, version file(s), tag format |
| `version.js` | pure: `parse`, `format`, `compare`, `successors(env, current, pkgVersion)`, `validateCandidate(...)`, `checkAgreement(...)` |
| `env-check.js` | pure `checkHosts(env, files → contents)`, plus a thin reader |
| `store.js` | wraps `@googleapis/chromewebstore` v2: `getStatus()` → `{ published, submitted, pendingReview }`, `upload(zipPath)` (with async polling), `publish()` |
| `zip.js` | `zipDir(dir, outFile)` via the system `zip -r -X` |
| `s3.js` | spawns the `aws` CLI: `whoami`, `readVersionJson`, `sync`, `writeVersionJson`, `invalidate` |
| `git.js` | spawns `git`: `assertClean`, `assertProdBranch`, `tagExists`, `restore(files)`, `commitAndTag` |
| `prompt.js` | `readline/promises`: `choose`, `confirm` (default No), `ask` |
| `shell.js` | promise-based `run(cmd, args, { capture })` that rejects on a non-zero exit code |

**Why**: the version rules are the riskiest part and must be unit-testable without network. Bash cannot test them cleanly, and the logic has outgrown `deploy.sh`.

**Alternative considered**: extending `deploy.sh` plus a Node helper for versions. Rejected: the logic would live in two places.

### D2. Official `@googleapis/chromewebstore` client (user decision)
This is Google's generated client for the Chrome Web Store API (v1.1 and v2), version 7.x, CommonJS, Node ≥ 22. It is pinned to an exact version: it went through three majors in one month (Sept–Oct 2026).

Usage:
- **Auth**: `new chromewebstore.auth.OAuth2(clientId, clientSecret)` + `setCredentials({ refresh_token })`. `google-auth-library` refreshes the access token. A service account can be added later through `GoogleAuth` without touching the callers.
- **Client**: `chromewebstore({ version: 'v2', auth })`.
- **Calls**:
  - `media.upload({ name: 'publishers/<pub>/items/<id>', media: { mimeType: 'application/zip', body: fs.createReadStream(zip) } })`;
  - `publishers.items.fetchStatus({ name })`;
  - `publishers.items.publish({ name, requestBody: { publishType: 'DEFAULT_PUBLISH' } })`.

Our own code covers what the client does not do:
- **Zip**: the system `zip -r -X <out> .` run inside `dist/chrome-ext-<env>/` (`zip.js`). If `zip` is not on `PATH`, pre-flight aborts (user decision). The archive goes to an `os.tmpdir()` folder and is deleted at the end.
- **Upload polling**: if `uploadState` is `IN_PROGRESS`, poll `fetchStatus` every 2 s until `lastAsyncUploadState` is `SUCCEEDED` or `FAILED`, with a 120 s timeout. The processed `crxVersion` must equal the chosen version.
- **Error mapping**: a `GaxiosError` becomes a single line with the HTTP status + `error.message` from the API body. The token is never printed.

**Alternatives considered**:
- `chrome-webstore-upload` (community, 2 dependencies, zip and polling included): rejected in favor of an official client.
- Raw `fetch`: rejected for the same reason.

### D3. `aws` CLI via `spawn`, not the AWS SDK
This matches `deploy.sh`, reuses the developer's existing profile and credentials, and adds no heavy dependency. `AWS_DEFAULT_REGION` defaults to `eu-south-1`, as before.

### D4. Remote version sources
- **Store**: `publishers.items.fetchStatus`:
  - `published` = highest `crxVersion` among the distribution channels of `publishedItemRevisionStatus`;
  - `submitted` = same for `submittedItemRevisionStatus`.
  - If the submitted revision is in state `PENDING_REVIEW`, abort: a new upload would conflict, and the operator must decide.
  - "Store version" for the agreement check = max(published, submitted). A previously submitted (e.g. rejected) version still consumed its number on the store.
- **S3**: `releases[/stage]/version.json`, `{ "version", "releasedAt", "commit" }`, written after each sync with `--acl public-read` and `--cache-control no-cache`. It also helps support ("what's live?"). If it is missing (first run), S3 drops out of the agreement check after an explicit confirmation.

**Alternative considered**: parsing a version banner out of `pundit.embed.js`. Rejected: the bundle has no banner, and adding one changes the build.

### D5. Version rules (pure, in `version.js`)
- Parse strictly with `/^(0|[1-9]\d*)(\.(0|[1-9]\d*)){2,3}$/`. The part count is 3 for prod and 4 for stage, each part ≤ 65535.
- Prod successors: patch, minor and major. The prompt is a numbered choice (default: patch) plus an option to type one by hand.
- Stage successor: a single value, derived from `package.json` against the base of `.stage.version` (see spec). A `package.json` version below the stage base aborts, because it means someone lowered `package.json`.
- Anything else is a jump. The script then shows the allowed successors and asks `Force <v>? [y/N]`, followed by the re-type confirmation. `--force-version <v>` takes the same path without the menu.
- Forced versions are still checked for format and for being strictly greater than every remote version. Those two are hard rules: the store rejects non-increasing uploads, and S3 going backwards would hide what is live.

### D6. Order of operations

```
preflight (clean tree, prod branch, zip + aws on PATH, aws whoami, CWS token, env domains)
  → read versions (local, store, S3) → agreement check
  → choose version → summary → CONFIRM 1
  → write version files → npm ci → npm run build:chrome-ext-<env> → verify artifacts
  → [dry-run: restore + exit]
  → zip dist/chrome-ext-<env> → store upload (draft, validated by Google; poll while IN_PROGRESS)
  → CONFIRM 2 ── no → restore files, report draft left on store, exit 0
  → store publish → s3 sync → version.json → CloudFront invalidation
  → git commit (version files only) + annotated tag
  → print "push with: git push --follow-tags"
```

- **Store upload before confirmation 2**: it is the only remote validation we get (manifest, version) and it is not public. Failing here costs nothing.
- **Store publish before S3**: the publish only submits for review and can be cancelled in the Dashboard, while an S3 sync is live immediately. If the publish fails, S3 is untouched.
- **Version files are written before the build**, because `postbuild` reads `package.json` / `.stage.version` to build the manifest. Before confirmation 2, any failure triggers `git checkout -- <version files>`.
- **Version files**:
  - prod: `package.json` + `package-lock.json`, via `npm version <v> --no-git-tag-version`;
  - stage: `scripts/.stage.version`.

### D7. Failures after going live
No automatic rollback. A tracker records the completed steps. On error it prints done/failed/pending and the literal remaining commands (with resolved paths, bucket, distribution ID, version), then exits 1. Re-running the script is not the recovery path: the agreement check would block it by design, since store and S3 would disagree.

### D8. Credentials
- Loaded from `scripts/.deploy.env` via `process.loadEnvFile()` (native in Node 22). That function does not override variables already set in the environment.
- The file is git-ignored; `scripts/.deploy.env.example` is tracked.
- Required variables: `CWS_CLIENT_ID`, `CWS_CLIENT_SECRET`, `CWS_REFRESH_TOKEN`, `CWS_PUBLISHER_ID`, `CWS_EXTENSION_ID_STAGE`, `CWS_EXTENSION_ID_PROD`. Optional: `AWS_PROFILE`.
- Secrets are never printed. Error messages name the variables only.

### D9. Environment domain check
The check is pure host extraction (`/https?:\/\/([^\/'"\s?#:]+)/g`) over the raw file text, against these rules:
- **Deny**: `localhost`, `127.*`, `0.0.0.0`, and `*.test` / `*.local` / `*.localhost` hosts.
- **Required API host**:

  | env | required | must not appear |
  |---|---|---|
  | stage | `api.thepund.netseven.work` | `api.thepund.it` |
  | prod | `api.thepund.it` | `api.thepund.netseven.work` |

The check runs on text, without importing the TS files, so it works without compiling.

**Alternative considered**: generating or restoring the config (e.g. via `render-env.sh`). Rejected (user decision): it couples the script to another repo, and the files are developer-owned.

### D10. Stage build stops bumping
`getStageVersion()` becomes `readStageVersion()`:
- it reads and validates the first line of `.stage.version`;
- it throws if the file is missing or malformed, instead of logging and returning `null` (a `null` manifest version would only be caught by the store).

`createManifestFile` uses it unchanged otherwise. The "reset `.0` when `package.json` changes" logic moves to `version.js` (stage successor).

### D11. Tests
Built-in `node:test` + `node:assert`. Files are `scripts/deploy/*.test.js`, run with `npm run test:scripts` (`node --test scripts/`). Jest stays Angular-only (`roots: src`, `jest-preset-angular`). Unit coverage:
- `version.js`: all spec scenarios;
- `env-check.js`: deny list, required and forbidden API host, third-party hosts.

`store.js` takes the API client as a parameter, so the status normalization and the upload polling (`SUCCEEDED` / `IN_PROGRESS` → `SUCCEEDED` / `FAILED` / timeout / `crxVersion` mismatch) are unit-tested with a fake client and a short interval. `s3.js`, `git.js` and `zip.js` are thin I/O wrappers, validated with `--dry-run` and a guided first stage release.

## Risks / Trade-offs

- **[Risk] Abort in the middle of the publish chain leaves a partial release** (store submitted, S3 not updated).
  → Mitigation: ordered steps, a tracker, printed recovery commands. Store before S3 limits the damage (a submission can be cancelled; S3 is not touched).
- **[Risk] `fetchStatus` field shapes differ from the docs or change** (V2 is recent).
  → Mitigation: `store.js` normalizes them in one place and aborts with the raw payload if it finds no `crxVersion`.
- **[Risk] Item visibility edited in the Dashboard blocks API publish** until one manual publish.
  → Mitigation: surface the store error verbatim; the README documents it.
- **[Risk] The refresh token expires or is revoked** (Google OAuth apps in "testing" status issue 7-day tokens).
  → Mitigation: the README requires the OAuth consent screen in production status, or a service account. Pre-flight fetches a token, so expiry fails before anything changes.
- **[Risk] Supply chain**: the official client pulls in about 45 packages (`googleapis-common`, `google-auth-library`, `gaxios`…) inside a process holding publish-capable credentials.
  → Mitigation: devDependency pinned to an exact version, installed only through the lockfile (`npm ci`), upgraded deliberately.
- **[Risk] `npm ci` is slower than `npm install`.**
  → Accepted: it is reproducible and never rewrites the lockfile, which would dirty the tree.
- **[Trade-off] Embed and extension are always released together.** A hotfix to one also releases the other with a new version.
  → Accepted (user decision): one version = one release, no drift.
- **[Trade-off] Stage versions follow `package.json` + `.N`.** A stage build that previews the next prod release still carries the previous prod base until `package.json` is bumped.
  → Accepted: matches the current convention.
- **[Risk] The existing tag `v1.9.2` and the live versions do not match the repo today.**
  → First run per environment: bootstrap S3 (`version.json` missing). If the store disagrees with the local file, align the local file by hand or use `--force-version`.

## Migration Plan

1. Merge this change. `deploy.sh` is removed and the README is updated in the same change.
2. One-time setup (README):
   - Google Cloud project with the Chrome Web Store API enabled;
   - OAuth client and refresh token for the account that owns both items;
   - publisher ID and the two extension IDs, written into `scripts/.deploy.env`.
3. Regenerate the stage config for the netseven stage (`render-env.sh`), then run `npm run deploy:stage -- --dry-run`.
4. First real stage release: S3 bootstrap prompt. If the store version differs from `.stage.version`, use `--force-version`.
5. Prod: create `local.prod.ts`, dry-run, release.

Rollback of this change: restore `deploy.sh` from git history. The S3 `version.json` files are harmless if left in place.
